## 9. Player Code Generator

Create a reusable JavaScript utility.

Suggested location:

```text
utils/
  playerCodeGenerator.js
```

Use Node.js built-in `crypto.randomInt()`.

Do not require another random-number library.

Do not use predictable sequential identifiers.

Do not derive Player Codes from:

- Email addresses
- Phone numbers
- Dates of birth
- Usernames
- Account creation timestamps
- MongoDB ObjectIds

Example candidate generation function:

```javascript
import { randomInt } from "node:crypto";

export const generatePlayerCode = (digits = 7) => {
  if (
    !Number.isInteger(digits) ||
    digits < 7 ||
    digits > 10
  ) {
    throw new Error(
      "Player Code must contain 7 to 10 digits"
    );
  }

  const min = 10 ** (digits - 1);
  const max = 10 ** digits;

  return randomInt(min, max).toString();
};
```

This function only generates a candidate code.

It does not independently guarantee database-level uniqueness.

## 10. Unique Code Allocation Algorithm

Implement a separate allocation/retry workflow around the generator.

The algorithm must:

1. Generate a random seven-digit code.
2. Check whether that Player Code is already allocated.
3. If occupied, generate another random code.
4. Repeat until an unused code is successfully allocated.
5. Escalate to eight, nine or ten digits after a configurable number of collisions.
6. Save the code with a MongoDB unique index enforcing uniqueness.
7. If a concurrent insert creates a duplicate-key error for playerCode, generate another candidate and retry safely.

Conceptual flow:

```text
User Registration
    ↓
Generate Random Numeric Code
    ↓
Check Existing Allocation
    ↓
Does Code Already Exist?
    ├── Yes → Generate Another Code
    └── No → Attempt Atomic Allocation
                  ↓
             Duplicate Key?
               ├── Yes → Retry
               └── No → Continue Registration
```

Use a configurable retry budget.

Do not implement an unbounded `while(true)` loop that can hang account registration indefinitely.

If the configured retry budget is exhausted, return a meaningful temporary allocation error.

No duplicate Player Code may be assigned.

Do not retry unrelated errors such as duplicate email, invalid password or database connection failure as though they were Player Code collisions.

## 11. Concurrent Registration Protection

Important scenario:

Two users register simultaneously.

Both random generators produce the same Player Code.

Both uniqueness prechecks return no existing record.

The MongoDB unique index must ensure only one allocation succeeds.

The other registration must regenerate its Player Code and retry the appropriate operation.

An application-level `findOne()` or `exists()` check alone is not sufficient.

Handle MongoDB duplicate-key error `11000` only when it relates to the Player Code allocation.

Prevent retrying registration side effects unnecessarily.

For example, do not send multiple welcome emails or create multiple UserProfile records because Player Code allocation was retried.

# PART C — H3 GEOSPATIAL ARCHITECTURE

## 18. H3 Resolution Strategy

Use two configurable resolutions.

| Resolution | Average Cell Area | Usage |
|---|---|---|
| 7 | Approximately 5.16 km² | Medium and larger-radius searches |
| 8 | Approximately 0.737 km² | Small-radius searches |

Configuration:

```javascript
export const H3_CONFIG = {
  fineResolution: 8,
  coarseResolution: 7,
  fineSearchMaxRadiusKm: 3,
  defaultSearchRadiusKm: 10,
  minSearchRadiusKm: 1,
  maxSearchRadiusKm: 20,
  maxCandidateCells: 800,
  enableGeoFallback: true
};
```

Use resolution 8 for searches within 1–3 km.

Use resolution 7 for searches greater than 3 km and up to 20 km.

These are initial configurable engineering defaults, not measured performance guarantees.

Do not assume an H3 cell or ring represents a fixed kilometre radius.

## 20. Calculate H3 Cells

Use the installed `h3-js` library.

```javascript

  res7: latLngToCell(latitude, longitude, 7),

```

Calculate both resolutions independently from the original coordinates.

Do not derive the geographic resolution 7 cell from the resolution 8 logical parent when actual geometric containment is required.

Remember:

- H3 uses latitude, longitude.
- GeoJSON uses longitude, latitude.

Calculate H3 cells on the backend.

Never trust client-provided H3 identifiers.

Update GeoJSON and H3 fields together.

# PART I — SIX MANDATORY H3 EDGE CASES

## 66. Empty Centre Hexagon

If the captain's immediate H3 cell contains no players, search all cells covering the selected radius.

Do not return false empty results.

If no eligible players exist within the complete selected radius, offer expansion.

Example:

- 5 km
- 10 km
- 15 km
- 20 km

Do not silently expand beyond the user's selected distance.

Automatic expansion requires explicit permission.

Return the actual final radius used.

If implementing ring traversal, handle pentagons, cell boundaries and distortion.

## 67. Duplicate Reads During Expansion

Naive cumulative `gridDisk` expansion repeatedly includes previously searched inner cells.

For fixed-radius searches, prefer one complete H3 cover and one indexed aggregation query.

For progressive searches:

- Track visited cells.
- Deduplicate candidate and returned user IDs.
- Avoid per-cell database queries.
- Use bounded query budgets.

Important:

A previously searched cell may partially overlap the newly expanded radius.

Querying only newly visited cells can miss eligible players.

Use appropriate geographical distance annuli and complete cell coverage when incremental radius expansion is implemented.

Do not sacrifice search completeness to avoid repeated queries.

## 68. Excessive H3 Candidate Cells

Firestore's fixed 30-item disjunction limitation does not apply directly to this MongoDB architecture.

Do not introduce Firestore batching.

Large MongoDB `$in` arrays can still be expensive.

Enforce configurable candidate-cell limits.

Deduplicate cell IDs.

If the threshold is exceeded, prefer MongoDB `$geoNear` fallback.

Do not truncate the covering-cell list.

If batching is introduced later, preserve complete coverage, global ordering, deduplication and pagination.

## 69. Dense City vs Sparse Town

Use configurable resolution 7 and 8 initially.

Dense areas may contain thousands of players per cell.

Sparse areas may contain very few.

For dense areas:

- Apply appropriate indexed filters.
- Use indexed sport lookups.
- Restrict fields.
- Paginate.
- Avoid loading every player into Node.js.

For sparse areas:

- Search complete approved radius.
- Return valid empty results.
- Offer explicit radius expansion.

Redis may store non-sensitive aggregate density metrics.

Do not overengineer dynamic density prediction initially.

Do not assume finer H3 resolutions always improve performance.
